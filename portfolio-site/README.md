# Leo Mabuku Portfolio

Professional Astro portfolio for Leo Mabuku: a fourth-year Computer Science student, software developer and entrepreneur in Kitwe, Zambia.

## Stack

- Astro and TypeScript
- Scoped/static CSS with Fontsource and Phosphor icons
- GSAP ScrollTrigger and Flip for scroll scenes, filtering and coordinated transitions
- Three.js for the deferred homepage portrait signal layer
- Vitest for content-refresh utilities
- GitHub Actions for scheduled public-repository refreshes
- Cloudflare Pages for static hosting

## Experience architecture

The interface keeps native scrolling and progressively enhances static Astro HTML. `src/scripts/experience.ts` is the route-level entry point: it initializes declarative `data-motion`, `data-scene`, `data-project-slug` and related hooks after Astro navigation, and disposes every listener, observer and timeline before the next route swap.

Motion is selected through the internal `MotionMode` contract:

- `full` enables the pinned hero scene, richer GSAP choreography and deferred WebGL portrait layer.
- `lite` keeps purposeful transitions while omitting WebGL and high-cost pointer effects on smaller, coarse-pointer, data-saving or lower-memory devices.
- `reduced` honors `prefers-reduced-motion` and keeps content immediately readable without motion dependency.

The original portrait, project evidence, navigation and contact paths always render without JavaScript or WebGL. Audio is never started, video previews are muted, and scrolling is never intercepted.

```sh
npm install
npm run dev
```

Quality checks:

```sh
npm test
npm run build
```

Motion-system coverage lives in `scripts/motion-system.test.ts`, including mode selection, session-only introductions, project filtering and cleanup idempotency. Visual comparison evidence and the final design audit live in `qa/` and `design-qa.md`.

## Content locations

- `src/data/site.ts` — professional profile, skills, education, experience, hackathons/awards and full case studies (including optional audience, market and production-path blocks)
- `src/data/projects.json` — generated public-repository cache used by the refresh workflow
- `src/pages/` — Home, Work, About, Resume and Contact routes
- `src/pages/work/[slug].astro` — static project case-study routes
- `public/images/projects/` — approved project evidence and screenshots (SmartWater Zambia has `web/` and `mobile/` sets)
- `public/images/hackathons/` — event photographs and certificate scans
- `public/documents/` — downloadable resume in PDF and Word formats

Hackathons and awards are maintained in the `hackathons` array in `src/data/site.ts` and render on the homepage, About and Resume routes.

To add or update a project, edit its record in `src/data/site.ts`. Never add private source, subscriber records, credentials or unapproved client information. Public repository metadata may be refreshed independently without overriding the curated case-study content.

## Resume

The Resume page provides approved PDF and Word downloads. Resume content is maintained in `src/data/site.ts`; the downloadable files are generated by `scripts/build-resume.py` and saved to `public/documents/`.

Regenerate both files with the bundled Python runtime after changing verified resume facts:

```sh
python scripts/build-resume.py
```

## Contact details

Approved public contact information lives in `src/data/site.ts`. The contact form creates a pre-addressed message in the visitor’s email application; it does not store or transmit form data through the site.

## Public repository refresh

The repositories used by the current case studies are explicitly included in `scripts/content-utils.mjs`, so they continue to refresh even when a GitHub topic is missing. Apply the `portfolio` topic to any new public repository that should become eligible for automated refresh. Forks, archived repositories and known empty or duplicate repositories remain excluded. The workflow must never fetch or publish private source, subscriber records or credentials.

See `PORTFOLIO_CONTENT_CHECKLIST.md` for remaining launch items.

## Content, editing from a phone, and the résumé pipeline

All site content lives in `src/data/*.json` and is validated with Zod inside `src/data/site.ts`. Astro pages, the résumé generator and the tests all read the same files, so there is only one place to edit.

**Editing from a phone.** `.pages.yml` (repository root) configures [Pages CMS](https://pagescms.org). Sign in at `app.pagescms.org` with GitHub, choose this repository, and you get forms for projects, experience, education, certifications, skills, hackathons, the profile and the résumé. Saving commits to GitHub, which triggers the Cloudflare build — roughly 1–2 minutes until it is live. `settings.content.merge: true` keeps every key the config does not describe, so saving a project cannot silently drop its media or audience blocks.

**Adding work.** Add an object to `projects.json` (or fill the form) with a unique `slug`; the case-study route, `/work/` listing, home page count and résumé options all pick it up on the next build. A malformed entry fails the build with a readable error instead of shipping.

**Résumé.** `npm run build` runs `scripts/build-resume.mjs` first (`prebuild`), rendering `public/documents/Leo-Mabuku-Resume.pdf` from the same JSON. `src/data/resume.json` controls the summary, which projects and roles appear, and the order.

**Your own PDF wins.** Set `source` to `"uploaded"` in `resume.json` (and point `uploaded.file` at a PDF under `public/uploads/`), or run:

```sh
npm run resume:upload -- ~/Downloads/Leo-Mabuku-CV.pdf   # ships your file untouched
npm run resume:revert                                    # back to the generated one
```

In `uploaded` mode the generator copies your file to `public/documents/Leo-Mabuku-Resume.pdf` and does not render anything, so a deploy can never overwrite a résumé you uploaded. The download URL never changes, so previously shared links keep working. `scripts/resume-pipeline.test.ts` fails if the generated PDF drifts from the data, or if an uploaded PDF does not match the file it is supposed to ship.

**Images.** Uploads from the CMS go to `public/uploads/` (served at `/uploads/...`). Keep large media there rather than in `public/images/`.

## Footer visit counter

`functions/api/visits.ts` is a Cloudflare Pages Function answering `GET /api/visits` with `{ available, total, today }`. It is aggregate-only: one integer for all time, one for the current UTC day. No IP addresses, no cookies, no user agent, no per-visitor records.

To switch it on, add a KV namespace to the Pages project once:

```sh
npx wrangler kv namespace create VISITS
```

Then in the Cloudflare dashboard → **Workers & Pages → leo-mabuku-portfolio → Settings → Functions → KV namespace bindings**, add a binding named `VISITS` pointing at that namespace, and redeploy.

Until the binding exists the endpoint returns `{ available: false }` and the footer counter stays hidden — nothing breaks. KV has no atomic increment, so simultaneous views can occasionally be missed; for a portfolio footer that is the right trade.
